# Employee Management System (EMS) — Backend

REST API backend that serves as a **system of record for employee information** across
multiple legally distinct organizations in India.

**This is not an HRMS.** It performs no payroll, payslip, income-tax/TDS, PF/ESIC/PT/LWF
contribution, attendance, leave, recruitment, performance, training, expense, asset or
full-and-final settlement processing, and it computes no net pay, gross totals, component
sums, deltas, percentages of a base, projections or cost-to-company figures. Salary
structures, statutory identifiers and dates are stored as **reference data only**
(specification §4.2, §4.3, AC-24).

The authoritative requirements are in [`EMPLOYEE_MANAGEMENT_SYSTEM.md`](EMPLOYEE_MANAGEMENT_SYSTEM.md).

- **Python 3.13+**

  controls the specification itself prescribes; see [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) §7.

## Setup

### 1. Install

```bash
python -m venv .venv
.venv/Scripts/activate          # Windows;  source .venv/bin/activate on Unix
pip install -e ".[dev]"
```

### 2. Configure

```bash
cp .env.example .env
python -m app.cli generate-keys    # prints SECRET_KEY and the two encryption keys
```

Paste the generated values into `.env` and set `DATABASE_URL`. The application **refuses to
start** on a placeholder secret, an undersized key, identical encryption and blind-index keys,
or a staging/production configuration that uses environment-held keys, local disk storage or
no malware scanner. That is intentional (§25.9, OWASP A02).

> **Upgrading from the previous HRMS in this repository:** the existing `.env` points at
> `hrms_dev_db`, which holds the unrelated v1 HRMS schema (67 tables, including the modules
> §4.2 forbids) whose table names collide with EMS. Point `DATABASE_URL` at the `ems` schema
> instead and add the two encryption keys. The v1 schema is left untouched. See
> `docs/DECISIONS.md` DEC-043.

### 3. Create the schemas and migrate

```bash
python scripts/create_databases.py    # creates `ems` and `ems_test`; never drops anything
alembic upgrade head
python -m app.cli check-db            # verifies version, isolation, sql_mode, timezone
python -m app.cli seed                # roles, permissions, states, identifier configuration
```

`seed` is idempotent. On a database that holds **no users and no organizations** it then
bootstraps a way in from `ORGANIZATION_NAME`, `SEED_ADMIN_EMAIL` and `SEED_ADMIN_PASSWORD`
(`.env`): one organization plus one local administrator holding SSA + OA + HRA, which between
them are every permission in the §5.3 matrix. Once any user or organization exists it is a
no-op, so re-running the seed never re-provisions an administrator. The administrator's
password, the organization's `entity_type` (`OTHER`) and its placeholder registered address
are all meant to be corrected before real data is entered, and the application refuses to
start with `SEED_ADMIN_PASSWORD` set in staging or production (§19).

### 4. Run

```bash
uvicorn app.main:create_app --factory --reload
```

- API: `http://127.0.0.1:8000/api/v1`
- OpenAPI: `http://127.0.0.1:8000/docs`
- Liveness: `/health` · Readiness: `/ready`

There is deliberately no module-level `app` object: building the application at import time
would validate the environment as a side effect of importing anything from `app.main`.

## Security posture

Short version; the detail is in `docs/ARCHITECTURE.md` and `docs/AUTH.md`.

- Tenant isolation at four layers: path authorization, service object checks, a mandatory
  organization filter in the repository layer, and composite foreign keys in the database.
- Permission-based authorization from a single §5.3 matrix; no endpoint branches on role names.
- Restricted fields are **omitted** from responses, not nulled; sensitive identifiers are
  masked from a stored last-four fragment with no decryption.
- AES-256-GCM field encryption with additional authenticated data binding each ciphertext to
  its organization, entity and field, so a blob cannot be relocated between rows or tenants.
- HMAC blind indexes, keyed per organization group, make cross-group identifier matching
  impossible by construction rather than by a query filter.
- Append-only audit records written in the same transaction as the change they describe.
- Structured logs with correlation ids and no personal data; request bodies are never logged.
- No stack trace, database error, token, key or raw identifier ever reaches a client.
